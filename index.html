Real-Time Multi-Tenant Collection Architecture (OneN)

AWS ECS Fargate • PostgreSQL PL/pgSQL Audit Triggers • CloudFront WSS

THE PROBLEM & CONSTRAINTS:

High-concurrency financial collections platform where concurrent updates caused race conditions and data corruption. Mixed-content SSL errors blocked real-time WebSockets, while cloud deployments lacked strict tenant boundary isolation and immutable audit logs.

THE ARCHITECTURAL SOLUTION:

Enforced strict multi-tenant isolation with PostgreSQL PL/pgSQL audit triggers logging every mutation. Built dual-origin CloudFront reverse proxy terminating HTTPS and proxying /socket.io/* over secure WSS without mixed-content drops. CI pipeline executes 34 live API suites on an ephemeral DinD test database.

Case Study 03 • Security & On-Premises Architecture

Standalone 2FA OTP & Digital Signature Microservice

Zero-Trust Challenge-Response • CoreDNS ClusterIP • Hybrid / On-Prem Bastion

Private VNet Subnet CoreDNS Internal ClusterIP Zero-Trust Bastion
Click to Zoom Full Diagram Zero-Trust Security Mesh
THE PROBLEM & CONSTRAINTS:

The client was locked into expensive third-party SaaS vendors for two-factor authentication and digital signing ($0.05+ per verification). Regulatory data sovereignty required keeping authentication payloads and cryptographic keys strictly inside private, on-premises or air-gapped cloud boundaries.

THE ARCHITECTURAL SOLUTION:

Developed a containerized asynchronous challenge-response 2FA microservice. Isolated the cryptographic signing engine inside a private subnet with zero public IP exposure, communicating exclusively over Kubernetes CoreDNS ClusterIP with mutual token verification. Multi-stage Docker packaging stripped build tools, achieving 0 Trivy CVEs. Node administration locked down via an SSH Bastion jumpbox with NSG IP whitelisting.

BUSINESS OUTCOME & METRICS:
$18K/yr recurring SaaS saved
100% On-prem/Hybrid compliant

Zero public attack surface

Case Study 04 • Asynchronous Task Processing

SubTrack: Distributed Async Subscription & Alert Engine

FastAPI Gateway • Celery Workers • Valkey/Redis Broker • PostgreSQL 18

FastAPI Gateway Celery + Valkey Broker PostgreSQL 18 + Alembic
Click to Zoom Full Diagram Distributed Async Queue
THE PROBLEM & CONSTRAINTS:

Synchronous scheduled alert loops caused heavy database locking, thread pool exhaustion, and frequent missed renewal notifications as subscription volumes grew. The system required guaranteed asynchronous task execution, queue rate-limiting, and high-concurrency ingestion.

THE ARCHITECTURAL SOLUTION:

Decoupled HTTP request handling from background processing. Built a non-blocking FastAPI + SQLAlchemy 2 API gateway paired with Celery Beat for cron dispatching and Valkey (Redis-compatible) for in-memory message queuing. Worker pools process thousands of scheduled renewal alerts concurrently with automated dead-letter retries, completely isolating the primary PostgreSQL database from heavy I/O spikes.

BUSINESS OUTCOME & METRICS:
99.98% Alert delivery rate
Zero database lock contention
Sub-15ms API response latency
Horizontal worker scalability
Client Takeaway: "Orchestrates background workers, message brokers, and caching layers to process scheduled workflows and alerts reliably at scale without locking databases."
FastAPI Celery Redis / Valkey PostgreSQL
